# Reuben: experimental continuous transfer pipeline

Reuben adapts the existing SDK file service to an already admitted, reliable ordered
RTCDataChannel. It is a prototype, not an enabled production transport. The public
SDK entrypoints and Phantom Share remain unchanged.

## Contract

- One binary message carries a complete chunk frame: RBN1 magic, chunk index,
  payload length, 32-byte file digest and payload. Header fields are network-endian.
  There is no separate metadata message that must be paired with a following payload.
- The receiver requests the whole file through the existing rolling window, default 32.
  Verified arrivals replenish requests within the existing 32-slot receive admission.
  There is no coordinator round trip after each 32 chunks.
- Source preparation stays bounded by the existing per-peer prepared-send queue.
  The sender awaits native bufferedamountlow capacity events. Timers only fail stalled
  work, never poll for capacity or grant it.
- Verification, immutable verified storage, four concurrent writes, cancellation,
  request deadlines and resume inventory reuse the real SDK file service.
- Completion sends a separate receipt after verified storage/assembly succeeds.
  It is not a per-chunk ACK and never gates further chunk submissions. The sender
  validates identity, manifest root, byte count and chunk count before emitting
  reubenReceipt. This is an authenticated peer's receipt, not independent proof
  that a malicious receiver retained the file.

The caller must provide admission, publication authorization and revocation via the
existing allowed/canUsePeer policies, bind the channel to the correct peer, and own
its lifecycle. This adapter does not replace discovery, signed distribution policy,
roster coordination or source selection. It sends protocol controls on its dedicated
channel; do not multiplex unrelated application messages onto that channel.

## Usage

Import createReubenTransfer from packages/phantom-core/experimental/reuben.js.
Create one adapter at each end. Supply channel, the remote peerId, authorization
hooks, a chunkStore, and emit. On fileOffer, request the offered manifest id with
peers containing the bound peer. publish and share expose the existing file-service
operations. On the source, reubenReceipt reports the receiver's completed file.

Pass the negotiated pc.sctp.maxMessageSize as maxMessageSize when known and finite.
The conservative default is 65536 bytes including the 44-byte header. publish
therefore defaults to 65492-byte payloads on that limit. With a 262144-byte negotiated
limit, 65536-byte payloads are supported. Do not assume every browser accepts a
65536-byte payload plus a header. The channel must be reliable and ordered.

Resumption requires retaining verified receiver storage and manifest identity,
creating a fresh adapter/channel if needed, sharing the same manifest, and requesting
it again. Verified indexes are skipped. No automatic reconnection or retry timer
is added by this adapter.

## Controlled comparison

Run from the repository root:

```sh
node --test tests/reuben.test.js tests/data-channel-capacity.test.js tests/file-pipeline.test.js tests/file-preparation.test.js tests/file-window.test.js
PHANTOM_REUBEN_OUTPUT=/tmp/reuben-results.json node tools/perf/reuben-comparison.mjs
```

The comparison uses the real current createNetworkDistribution implementation and
the real Reuben/file-service implementation. Both transfer identical generated bytes,
use 64 KiB payloads, a 32-request window, the same memory storage with 8 ms write delay,
and the same configured bandwidth and propagation. Each result independently verifies
the complete SHA-256. Runs reverse engine order on the second repetition.

Timing excludes source hashing, initial channel setup and manifest exchange on both
engines. The current engine starts at its first batch request; Reuben starts at its
whole-file request. Completion includes storage/assembly. Setup and total durations
are reported separately. The current engine's original coordinator and continuation
path stay intact; the harness uses its existing 10 ms scheduler option.

The model serializes application messages per direction. Its recovery case inserts
one RTT plus one 1200-byte serialization cost every eighth binary message, holding
ordered delivery. It is a deterministic scheduling stress, NOT an SCTP implementation,
congestion controller, real packet-loss process, NAT path, Chrome or radio simulation.
No throughput result here establishes a device ceiling or fixes the observed 5G drain.

Reports retain measured peak native-model buffered bytes, empty-buffer time after
first binary submission, peak concurrent writes, correctness and recovery counts.
These are queue measurements, not total process memory or browser memory estimates.
The supplied memory store intentionally retains the complete file at the receiver.

An optional sustained case can be reproduced with:

```sh
PHANTOM_PROFILE_BYTES=33554449 PHANTOM_REUBEN_CASE=80ms-rtt PHANTOM_REUBEN_OUTPUT=/tmp/reuben-sustained.json node tools/perf/reuben-comparison.mjs
```

Recorded results are in tools/perf/reuben/results.json and results-sustained.json.

Node tests passed. These results support further development of continuous scheduling;
they are not a claimed fix for the physical-device internet slowdown. Browser/5G
validation and integration with authorized distribution scheduling remain outstanding.
