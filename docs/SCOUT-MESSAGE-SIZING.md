# Message-size comparison before the file

The v7 transfer scout accepts `comparison: 'queue' | 'message'`; the distribution option is `scoutComparison`. SDK callers retain queue comparison by default. Share selects message comparison. The v7 capability name and wire version prevent an older v6 peer from interpreting the different comparison schedule. Peers without the shared scout capability still use the existing negotiated file-transfer defaults.

Message comparison replaces the four existing queue passes with a 256 KiB / 16 KiB / 16 KiB / 256 KiB comparison (or reversed order). Every pass uses the same selected associations, payload byte count, and 16 MiB high / 4 MiB low queue boundary. Actual messages are capped by each association's negotiated limit; an unavailable limit retains the existing 64 KiB conservative ceiling. If negotiation makes both profiles identical, no size winner is declared. Per direction this still sends four 9 MiB comparison payloads with the default sample size, not additional test rounds or payload.

A 16 KiB source-message policy requires repeated sender total and late delivery improvement under the existing 10% rule, then matching receiver reports that confirm the speed gain with no worse maximum-gap envelope. Missing, overlapping, interrupted or contradictory evidence leaves message sizing at its negotiated defaults. Queue boundaries are held fixed, not claimed optimized. A message policy cannot apply to a different final lane set.

On success, only the retained source associations for the selected generation and asset receive the message-size policy, and only with negotiated `phantom-file-fragments-v1` support. Existing fragment metadata and reassembly carry the original verified hash chunks; the manifest, chunk size, hashes and storage path do not change. Each actual message and wrapper is still checked against the target transport's limit. Source policy application is exported separately from queue-policy application. No timers, retries, polling or mid-transfer tuning are added.

This is an experiment in SCTP message scheduling, not a claim that 16 KiB is an IP MTU or will fix the measured Android UDP receive drops. Native socket buffer capacity remains inaccessible to browser code. The real Chrome test uses controlled policy timings to force a winning small-message choice, then transfers and reassembles real data with every binary message at most 16 KiB and a matching checksum. That verifies policy enforcement and interoperability, not WAN speed improvement.
